# Mosaic Threat Model

Status: v1 draft (M0). It is reviewed at every milestone and fully re-run in M9.
Crypto details are in `CRYPTO_SPEC.md`, and section references (§) point
there. Extension specifics will be expanded in `EXTENSION_SECURITY.md` (M4).

## 1. Assets

| ID | Asset | Worst outcome if lost |
|---|---|---|
| A1 | Item plaintext (passwords, TOTP secrets, passkey private keys, notes, files) | account takeover everywhere |
| A2 | Master password, Secret Key | full vault compromise |
| A3 | Unwrapped keys in memory (AK, VK, isk) | full vault compromise while unlocked |
| A4 | Integrity of items (URL ↔ credential binding) | credentials filled into phishing sites |
| A5 | Availability of the vault (sync data, local DB) | lock-out, data loss |
| A6 | Metadata (who shares with whom, item counts, usage times) | privacy loss |
| A7 | Build and release pipeline, signing keys | malicious update to every user |

## 2. Trust boundaries

```
 [User] ─ UI ─ [Desktop app (Tauri) ── core (Rust)] ── IPC ── [native-messaging host] ── stdio ── [Extension background SW]
                       │                                                                         │ runtime messages
                       │ TLS 1.3                                                                  [Content script] ── DOM ── [Web page (untrusted)]
                       ▼
                 [Sync server (axum)] ── [PostgreSQL]
 [CLI] ── core ── TLS ──┘           [Mobile app + OS autofill/passkey provider] ── core (UniFFI)
```

Untrusted: web pages, the network, the sync server (honest-but-curious at
best, malicious at worst), other extensions, import files, and anything
received over IPC before authentication.

Trusted: the OS kernel and the logged-in user's session (with the caveats in
P5), the browser's extension isolation, the Rust core, and the platform
keystores.

## 3. Attacker profiles

| ID | Attacker | Capabilities | Goal |
|---|---|---|---|
| P1 | **Stolen server DB** (or malicious server operator) | full DB and server code, can modify responses, cannot break crypto | read vaults, inject data, track users |
| P2 | **Malicious website** | arbitrary HTML/JS/CSS, iframes, lookalike domains, timing | get credentials filled or exfiltrated, clickjack the user |
| P3 | **Malicious extension in the same browser** | its own permissions, can message other extensions and read/modify page DOM if it has host permissions | read filled credentials, spoof messages to our extension or native host |
| P4 | **Network attacker** | MITM, DNS spoofing, captive portals | read or modify sync, downgrade TLS, steal fills on HTTP |
| P5 | **Local malware without admin/root** | runs as the user: reads user files, connects to user-level IPC, screenshots, clipboard, keylogging in some OSes | read vault, approve actions as user |
| P6 | **Lost or stolen device, locked** | disk and hardware, offline time | decrypt vault |
| P7 | **Lost or stolen device, unlocked** | physical access to a running session | read or export vault, change master password |
| P8 | **Compromised build dependency** | malicious code in a crate or npm package, or in a GitHub Action | exfiltrate secrets at runtime, backdoor releases |

Out of scope (stated in the README and `SECURITY.md`): malware running as
admin/root or kernel-level, a compromised OS or hardware, cold-boot or DMA
attacks on a running machine, and coercion of the user. Partially in scope:
P5. We raise its cost, but a user-level attacker who is actively watching an
unlocked session can usually read what the user sees.

## 4. STRIDE per component

Mitigations name the milestone in which they are implemented and tested.

### 4.1 Rust core (`crates/core`, `totp`, `generator`, `passkey`, `import`)

| STRIDE | Threat | Mitigation |
|---|---|---|
| S | Forged ciphertext accepted as a real item | AEAD with ID-bound AAD (§7.2), M1 |
| T | Item moved between vaults or items swapped by the server | `vault_id` + `item_id` in AAD, M1 |
| T | Rollback to an old item version | authenticated version vector in plaintext, monotonic acceptance (§10), M2/M6 |
| R | User disputes a change | per-item history and device ID in plaintext, M2 |
| I | Secrets leaked via logs, panics, `Debug`, crash reports | redacting secret types, lint rules, `panic=abort`, M1 |
| I | Length leakage | padding (§7.2), M1 |
| I | Timing side channels in comparisons | `subtle`, constant-time library code, M1 |
| I | Secrets left in memory after lock | `zeroize`, minimal lifetimes, M1. Swap is a residual risk (ADR-0005). |
| D | Malicious import file causes OOM or hang | bounded parsers, size limits, fuzzing, M3 |
| D | Hostile server sends huge Argon2 parameters | upper bounds (§5.3), M1 |
| I | Passkey private keys read from an import file or written to an export file | Import: keys are decoded strictly into zeroizing buffers, validated and re-encoded by `Es256Key` (ES256 only), never in an error or a preview (it carries titles and counts); fuzz target `cxf`, M5 T4. Export: the master password again (the re-authentication is taken and spent), a plaintext warning, the file built in one zeroizing buffer and written by `write_file_atomic` (mode 0600 on Unix; on Windows the file inherits the folder's ACL; no system temp file), random account and item IDs per export (the file carries no vault or item ID), `handler_tests.rs`, M5 T4. Import also canonicalises and validates each rp ID and caps the passkeys per entry and per file before parsing their keys (hostile CXF file). Residual: R52 |
| E | Memory-unsafety exploit in a parser | `#![forbid(unsafe_code)]`, fuzzing, M1+ |
| I | A passkey private key leaks, or a signature or encoding is wrong | Keys live in the zeroizing `Es256Key` / `SecretVec`, never `Clone`, redacted `Debug`, not a `SecretField`; ES256 signatures are RFC 6979 deterministic; known-answer tests V1 to V11 (CRYPTO_SPEC §16) and an independent `node:crypto` verifier check every encoding, M5 |

### 4.2 Desktop app (Tauri)

| STRIDE | Threat | Mitigation |
|---|---|---|
| S | Another local process impersonates the native host on IPC | peer verification (process path and code signature) plus a pairing key, M4 |
| S | A local process asks the SSH agent to sign | every signature needs an approval in the app (allow once; allow for 15 minutes, bound to key and client executable, only where the OS names the executable; deny), refused after 25 s, on lock and when 4 prompts are open; Deny has the initial focus and the allow buttons wait 1 s; listing public keys needs no approval (as in OpenSSH); RSA, P-384/P-521, DSA, certificates, key add/remove/lock and every extension are refused; off by default and running only while unlocked (ADR-0025), M3 |
| T | Malicious webview content (XSS in rendered item fields, import previews, insights hosts) | strict CSP, no remote content, React escaping, no `dangerouslySetInnerHTML` (a static test enforces it), a narrow Tauri capability allow-list, M3 |
| T | Hostile import file | parsed in Rust only, with file, entry, depth, decompression and KDF limits checked before the work starts; HMAC blocks verified before decryption; the webview gets titles, counts and warnings; parsed data dropped on commit, cancel, a new preview or lock; six fuzz targets (ADR-0021), M3 |
| R | Silent export or change | an audit log for export, password change and share, together with the first of those features (M6); M3 has none of them |
| I | Clipboard sniffing | Rust writes the clipboard and marks it excluded from history and monitoring (Windows `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory = 0`, `CanUploadToCloudClipboard = 0`; macOS `org.nspasteboard.ConcealedType`; Linux X11 `x-kde-passwordManagerHint`); it clears after 30 s by default (10 s to 5 min, or off after re-authentication) on the monotonic or wall clock, only if the clipboard still holds Mosaic's value, and on lock and quit (ADR-0020), M3. Residual: R21 |
| I | Screen capture of revealed secrets | reveal on demand only; hidden after 60 s, on blur and on lock; `contentProtected` (Windows `WDA_EXCLUDEFROMCAPTURE`, macOS `NSWindowSharingNone`), M3. No effect on Linux (R21) |
| I | QR scan sees everything on screen | capture only on a click on *Scan screen*, one frame per display; pixels only in zeroizing buffers, wiped when the search ends; never on disk, in logs or in the webview; only an `otpauth://` payload is kept, other QR content is dropped without reporting it; not offered on Wayland (the portal writes a file) or macOS (ADR-0031), M3. Residual: R30 |
| T | Hostile image (file or clipboard) with a decompression bomb or malformed data | PNG/JPEG only by magic bytes, file ≤ 20 MiB checked before reading, ≤ 16384 px per side and ≤ 40 MP from the header before decoding, `image::Limits` 512 MiB, pure-Rust decoders, frames downscaled to ≤ 8 MP before QR detection, one scan at a time, a fuzz target over image → QR → `otpauth://` (ADR-0031), M3. Residual: R31, R32 |
| S | A malicious or swapped QR code (a phishing page shows a code labeled with another service) | nothing is saved without the confirmation screen (issuer, account, digits, period, live code); labels pass `mosaic-totp`'s label rules (no controls, bidi or invisible characters); several different codes are refused rather than guessed (ADR-0031), M3 |
| I | The secret leaks to the webview during setup | scans keep the parsed secret in Rust behind an opaque pending ID (10 min, cleared on lock and on save); the webview gets a secret-free preview and the 30-second code only; manual entry is the one path where the user types it (R19) (ADR-0031), M3 |
| I | Copies of the QR screenshot outside Mosaic | after reading a pasted screenshot Rust empties the clipboard and the UI names clipboard history, the Snipping Tool's auto-save and saved screenshot files (ADR-0031), M3. Residual: R31 |
| I | Unlocked vault on an unattended machine (P7) | auto-lock on idle (default 10 min, measured on the monotonic and wall clocks), on resume from sleep (clock gap) and, on Linux, on logind sleep and screen-lock signals; the triggers cannot all be turned off (CRYPTO_SPEC §11), and turning one off needs the master password; re-authentication before saving the Emergency Kit again, M3. Windows and macOS have no screen-lock or user-switch signal without unsafe FFI (R21) |
| I | Secret Key at rest on the device | OS keystore (Windows Credential Manager/DPAPI, macOS login Keychain, Linux kernel keyring per login session); a keystore failure falls back to typing the key from the Emergency Kit (ADR-0020), M3 |
| I | Quick unlock bypasses the master password | Opt-in, needs the master password to enrol (enforced by the vault API through a session-bound proof valid for 120 s), once per app start, and again after at most 30 days (default 14); hardware-bound platform keys (TPM-backed Windows Hello key, Secure Enclave key with biometry-only access); expiry or a failed unwrap deletes wrapping and platform key, M3 (ADR-0028). Residual: R23 |
| T | A local process edits `settings.json` to switch off auto-lock or clipboard clearing, or to lengthen the quick-unlock age | the protection settings carry an HMAC under a key derived from AK (CRYPTO_SPEC §11.1, ADR-0030): while locked only values at least as strict as the defaults apply; after unlock a missing or invalid MAC resets the weakening fields, rewrites the file and tells the user once. Residual: R28 |
| I | Secrets in the webview heap | R19 |
| D | Corrupted local DB | SQLite WAL, integrity check, server re-sync, M2/M6 |
| D | SSH agent flooding | at most 32 connections, 4 open prompts, 256 KiB per message, a 10 s body timeout; on Windows another local account can hold the connection slots through the pipe's default DACL (R20), M3 |
| E | Webview reaches the Tauri API surface | the capability grants only Mosaic's own commands (no `core:*`, no plugin with a JavaScript API, no opener, dialog, fs or clipboard plugin, events over a `Channel`); file and save dialogs and the global shortcut are driven from Rust; typed inputs validated in Rust; strict CSP; frozen `Object.prototype`; no devtools in release builds (ADR-0019, ADR-0020, M3). Tauri's isolation pattern is declined (ADR-0084): its AES-GCM layer is outside CRYPTO_SPEC §2 and its hook could only repeat the Rust-side checks; the red-team surface tests and the JavaScript dependency review (M9 T7) stay the compensating controls |
| I | A script or link sends the vault window to another page: data out in the address (the CSP does not cover top-level navigations), a remote page asking for the master password, or `http://tauri.localhost:<port>/` served by any local process, which Tauri counts as the app's own origin and so lets it call Mosaic's commands (R33) | a navigation guard (`navigation.rs`, a plugin on the app builder) refuses every load except the bundled frontend (`http://tauri.localhost` on Windows, `tauri://localhost` elsewhere, without port or credentials; the Vite dev server only in builds without `custom-protocol`); `window.open` is refused because no new-window handler is set; item URLs render as text; the capability names only `main` and no remote origin; a forged invoke key gets no answer (red team 2026-11-04), M3 |
| E | Malicious update or a tampered download | no in-app updater until the owner decides (OD-M9-5); releases carry a minisign signature over `SHA256SUMS` made in the CI environment `release` with the owner's approval, Authenticode and Developer ID with notarization where certificates exist, and updater artifacts signed with a separate key (CRYPTO_SPEC §17, ADR-0081, ADR-0082), M9. Residual: R118, R119 |
| S/T | The desktop opens the system browser for a WebAuthn handoff: a request that makes it open another URL, or a changed server address that sends the user to another site | one Rust function (`webauthn_flow::open_handoff`) builds `<canonical origin>/webauthn/#<id>` from the stored canonical origin and the handoff ID; no IPC request carries a URL and a static test pins one call site of the opener (`opener_has_one_call_site`); the webview still gets no opener permission (ADR-0077), M9. Residual: R124 |
| T | A hostile attachment (synced, imported or shared) attacks the image decoder when it is previewed | PNG and JPEG only by magic bytes, the ADR-0031 limits (16384 px per side, 40 MP from the header before decoding, 512 MiB decoder allocation, 50 MiB file), memory-safe Rust decoders, one preview at a time, no PDF or other parser, the same decoder surface as the QR scan (ADR-0034), M3. Residual: R34 |
| I | Decrypted file content outside zeroizing memory (preview pixels, Save as) | preview pixels only as downscaled RGBA through one binary IPC response painted into a canvas (no URL, blob or file in the webview), nothing decrypted kept in Rust between calls, the webview buffer zeroed after painting and the canvas cleared on close, lock and blur, `contentProtected` window, no thumbnails and no temporary files (ADR-0034), M3. Residual: R35 |
| I | Save as writes plaintext to disk | only on an explicit click, only to the path the native save dialog returns (which also confirms overwrites), a sanitized suggested name (spoofing characters, separators, device names, trailing dots), temporary file then rename, mode 0600, Mark of the Web on Windows (ADR-0034), M3. Residual: R36 |
| E | The webview names a file to read or overwrite | the four attachment requests carry IDs only and refuse every other key; paths come only from native dialogs that Rust opens; no fs or dialog permission in the capability; the size is checked before reading and the read is bounded; the quota is checked before encrypting (ADR-0034, `attachment_requests_refuse_path_keys`), M3. Residual: R37 |

### 4.3 Browser extension (highest risk)

The extension holds no vault and no master password; the desktop decides every match and
returns one credential per fill (ADR-0035, ADR-0037). The attacks below and the test that
covers each are listed in `docs/EXTENSION_SECURITY.md`; the hostile pages live in
`apps/extension/test/hostile-site/`.

| STRIDE | Threat | Mitigation |
|---|---|---|
| S | Phishing site that looks like the real one (P2) | The desktop matches the exact origin (scheme, host, port) by default; the extension sends the frame's own `location.origin`, never a value the page supplies. A look-alike or homoglyph host gets no match and no fill; an `xn--` host is shown in Unicode as a warning (`lookalike.spec.ts`), M4 |
| S | Page or other extension sends spoofed `runtime` messages (P2, P3) | The background answers popup operations only on a port named `popup` from the extension's own `popup.html` (`sender.id`, `sender.url`, no `sender.tab`); the content messages are `captured` and, with passkeys on, the bridge's two passkey messages (exact keys and limits), all from our id with a tab and rate limited; everything else is dropped without a reply. `externally_connectable: {ids: []}`, no external listeners, no `web_accessible_resources`. `content.js` and `capture.js` never listen to `message`/`postMessage` (`check-dist.mjs` greps for it) and accept `runtime` messages only from the background; the passkey bridge listens only to its own window (`event.source === window`) and answers only the shim's exact message shape (`router.test.ts`, `bridge.test.ts`, `spoof-messages.spec.ts`), M4, M5 T3 |
| T | Page restyles or overlays injected UI (clickjacking) | There is no injected UI: the extension adds no DOM to pages. Trusted gestures come only from the toolbar popup, the `fill-login` command and the context menu, which the browser draws (ADR-0035). A synthetic event cannot trigger any of them (`synthetic-events.spec.ts`), M4 |
| T | Hidden fields harvest extra data | Only fields a person could see and click are filled: `isFillable` checks CSS visibility, size (4 px), combined opacity (0.2), position inside the document and, on screen, that the field is on top at one of five points. The check runs at probe and again at fill time, so fields changed or injected in between are classified anew (`visibility.test.ts`, `hidden-fields.spec.ts`, `overlay-occlusion.spec.ts`, `type-swap-and-late-inject.spec.ts`), M4. Residual: R46 |
| I | Auto-fill on load exfiltrates credentials | Never. The content script is injected on demand after a user gesture (`activeTab`); nothing is injected or asked of the desktop on page load (`autofill-on-load.spec.ts`), M4 |
| I | Cross-origin iframe receives a fill | Refused: only the top frame, or a same-origin frame whose every ancestor is same-origin and visible and only after a confirmation click in the popup, is filled; cross-origin, sandboxed and opaque-origin frames and A-B-A nesting never are, and the desktop refuses a frame whose origin differs from the tab's (`frames.test.ts`, `frame.test.ts`, `cross-origin-iframe.spec.ts`, `same-origin-iframe.spec.ts`, `nested-a-b-a.spec.ts`, `sandboxed-srcdoc.spec.ts`), M4 |
| I | Content script compromised by page (shared DOM) | The content script runs in the isolated world, receives one credential for one frame at fill time, writes only field values, and drops every reference after the fill. It stores nothing and the page sees values only as input events (R41, R40), M4 |
| I | Fill races: the page navigates or changes between the click and the fill | The credential is delivered to the probed document only (`documentId` pinning on Chromium); the content script checks `location.origin` against the expected origin, the frame's ancestry and visibility again, and re-detects fields before it writes (`navigate-after-probe.spec.ts`, `type-swap-and-late-inject.spec.ts`), M4 |
| I | Fill over HTTP read by a network attacker (P4) | Refused unless the item's URL carries the per-URL HTTP override; decided by the desktop, which also refuses the https login on the http version of a site (`http-page.spec.ts`), M4 |
| I | The save capture script reads what the user types, or a page makes it report a login | Off by default; turning it on asks for the optional site access and registers `capture.js` (never in the manifest). It listens to trusted clicks on submit controls and the Enter key only (not `submit`, which the browser also raises for a script's `requestSubmit()`), reads one form's fields, sends one message per 2 s, and never listens to page messages. The background takes origin and tab from the browser, drops cross-origin, opaque and hidden frames and sites marked "Never", keeps the password in `storage.session` for five minutes bound to the tab's origin, and asks the desktop, which confirms in its own dialog (`capture.test.ts`, `save.test.ts`, `e2e/save.spec.ts`, R44), M4 |
| D | Page floods the extension with events | Rate limits in the background (content messages 10 a second and `captured` 5 a minute per tab, in-flight cap of four requests to the host, 20 s request timeout) and in the desktop (per op and pairing, see NATIVE_MESSAGING §6) (`router.test.ts`, `native.test.ts`), M4 |
| E | Over-broad permissions abused after compromise | Exactly `activeTab`, `scripting`, `nativeMessaging`, `contextMenus`, `storage`; no `host_permissions` (host access exists only as the optional permission that the opt-in save capture requests, T4); a manifest test and `check-dist.mjs` enforce the list, and the production package contains no test code (`manifest.test.ts`), M4 |

### 4.4 Native messaging channel

The extension reaches the desktop through the host binary `mosaic-native-host`
and a local endpoint (ADR-0036, `docs/NATIVE_MESSAGING.md`, CRYPTO_SPEC §15).

| STRIDE | Threat | Mitigation |
|---|---|---|
| S | Another extension launches our host (P3) | the host manifest lists only our extension IDs (`allowed_origins`, `allowed_extensions`); the host checks the caller argument against the pinned IDs (store IDs; the dev ID in debug builds only, R39) and exits with code 2 without connecting otherwise, M4 |
| S | Local malware talks to the desktop directly (P5), or an impostor answers the host | pairing is approved once in the desktop (the user compares a code and clicks Allow after a 1 s guard; only while unlocked; one request at a time; at most 3 a minute; a block after 3 denials). Every connection runs a mutual PSK handshake with HMAC proofs over both nonces, desktop first, and then AEAD frames with strict sequence numbers (CRYPTO_SPEC §15). Same-user malware that reads `K_pair` is not stopped (R38, R45), M4 |
| S | Another OS user or sandboxed process reaches the endpoint, or squats it | Unix: the socket is in a `0700` directory, the socket is `0600`, the server checks the peer UID and the client checks the directory's mode and owner and the peer's UID. Windows: a random pipe name per desktop start, created as first instance with remote clients rejected, published in a file in the user's profile that other accounts cannot read; the desktop holds a lease (an open handle that denies shared writing) on the file, and the host refuses a file nothing holds, so a stale name is never trusted (R42), M4 |
| T | Frames altered, replayed, reordered or reflected in transit | XChaCha20-Poly1305 per direction, the direction and pairing ID in the AAD, the header authenticated, strict sequence numbers, a closed connection on the first failure, M4 |
| I | Vault data leaked over the channel | there is no list or dump API: `search` returns at most 20 summaries without secrets; a secret leaves the desktop only for a fill of a matching item (one credential), as a generated value, or through a desktop-side clipboard copy; the host forwards an allowlist of ops and never parses bodies, M4 |
| I | The channel's secrets in memory | `K_pair` and the session keys sit in zeroizing types in the host and the desktop; the host keeps request and response bodies borrowed from zeroizing frame buffers, serializes into exactly sized zeroizing buffers, and a session that failed to open a frame is poisoned; the JSON parser, tokio's and std's stdio buffers leave residue (R40), M4 |
| D | Oversized or malformed frames, floods | 256 KiB frame cap on both links, checked before the payload is read; length 0 or a truncated frame is an error; the host exits with code 3 on a malformed browser frame; at most 8 connections, 4 requests in flight per connection and 16 pairings; per-pairing rate limits in the desktop; decoders fuzzed (`crates/native-messaging/fuzz`), M4 |
| E | The extension reaches commands it should not | the desktop serves only the ops of the protocol (`Op` allowlist, anything else is `invalidRequest`); unlock, lock, item reads, exports, imports and settings are not ops, M4 |
| S/T | A same-user process points a browser at its own host through a per-user manifest or an HKCU key, or replaces the host binary | release installs own the host and its manifests: a per-machine MSI in `%ProgramFiles%` with HKLM keys, deb and rpm with system manifests under `/etc` and `/usr/lib`, the host inside the signed app bundle on macOS (the desktop repairs the per-user manifests at start). `audit_manifests` checks the per-user locations at start and in Settings → Browser and shows `browserConnectorForeign` with Repair; `mosaic-native-host check` prints the same (ADR-0082, ADR-0083), M9. Residual: R121, R38 |
| T | The extension writes to the vault, or a page feeds it a fake login to save | `proposeSave` writes nothing: the desktop shows a dialog (title, vault, new or update, the HTTP override), allows it only after 1 s, keeps the captured password in Rust (the webview sees a mask) and drops it on cancel, expiry, lock and disconnect; an update can only change a candidate login's password; one prompt at a time, 3 proposals a minute, M4 |
| S | A page, or a compromised extension context, makes the desktop create or use a passkey for another site (rpId spoofing, an iframe, a look-alike host) | The origin and the top-level origin come from the browser and must be equal (`crossOriginFrame`) and https (`insecureOrigin`); the desktop checks the relying party ID itself with `mosaic-origin` and the public suffix list (`webauthn_rp_id`: a domain at or under the origin's registrable domain, not a public suffix, else `rpIdMismatch`) and builds `clientDataJSON` itself from the browser's origin. A site with no matching passkey gets `passkeyNotFound` without a dialog; only ES256 is made (`passkeyUnsupported`). `browser_tests.rs` (`requests_that_cannot_be_answered_open_no_dialog`), M5 T2. Residual: R50, R51 |
| T | The extension signs or writes without the user | `passkeyCreate` and `passkeyGet` write and sign nothing until the user chooses in the desktop dialog (1 s Allow guard, account or vault picked there, the dialog shows the rp ID and the origin's host). The answer is applied in Rust before the site is told: a create stores the item first, an assertion with a counter above 0 stores the raised counter first (`PendingAssertion`). A lock, a disconnect, a removed pairing, the page aborting or 300 s close the dialog and answer `cancelled`; a second request is `busy`; limits of 3 creates, 10 sign-ins and 20 cancels a minute per pairing, and 2 creates and 6 sign-ins a minute for each site, M5 T2 |
| E | UV is claimed without a verification | The UV flag is set only when the site did not say `discouraged` and the user unlocked or typed the master password within 300 s; otherwise the dialog asks for the password (`reauthenticate`, the five-failure lock applies, the password is cleared in the webview after each try), M5 T2. Residual: R49 |
| I/S | Page tampers with the passkey shim or forges its messages | The shim channel is page-visible by design (the page can replace the shim, read its messages and forge answers); it gains the page nothing beyond `navigator.credentials` for its own origin. The trust boundary is bridge, background, desktop: origin and frame come from `MessageSender` and must equal the bridge's `window.origin`, only the top frame is served (`allFrames: false`, `frameId` 0), the tab must still show that site, the request ID is made in the background, the rp ID is checked in Rust with the public suffix list, `clientDataJSON` is built in Rust, and every create and sign-in needs the desktop dialog. The scripts exist only after the opt-in; anything not handled goes to the browser's own WebAuthn, also a request the pairing's shared rate windows refuse, so one site cannot fail another's calls; a request aborted or left before it was sent never reaches the desktop (`passkey-shim-tamper.spec.ts`, `passkey-rpid-spoof.spec.ts`, `passkey-iframe.spec.ts`, `passkey-fallback.spec.ts`, `passkey-forge-frames.spec.ts`, `passkey-budget.spec.ts`, `passkey-lifecycle.spec.ts`, `src/background/passkey.test.ts`, `browser_tests.rs`), M5 T3. Residual: R47 |
| I | A passkey's private key or the list of passkeys leaves the desktop | no op lists, returns or exports a key: `passkeyCreate` returns the new credential's public key (SPKI) and `passkeyGet` a signature; the key is not a `SecretFieldKey`, so no reveal, copy, event or `ItemDetail` field reaches it; trashed passkeys and passkeys in hardware-protected or closed vaults are never offered. The `redteam` tests search every view and every op answer for the key in hex, base64 and base64url (`a_passkey_private_key_reaches_no_command_and_no_item_view`, `redteam_no_browser_op_returns_a_private_key`), M5 T2 |

### 4.5 Sync server

| STRIDE | Threat | Mitigation |
|---|---|---|
| S | Credential stuffing or online guessing | OPAQUE plus rate limiting per IP and per account, optional account 2FA, M6 |
| S | Offline guessing after DB theft (P1) | OPAQUE input includes the 128-bit SK (§9.2), M1/M6 |
| T | Server injects or alters records | AEAD, HPKE Auth shares, authenticated tombstones, M6 |
| T | Server serves old data (rollback/freeze) | monotonic version vectors, checkpoint freeze detection (§10), M6 |
| R | Disputed account actions | append-only audit log without secrets, M6 |
| I | Metadata analysis (P1) | minimal metadata (CRYPTO_SPEC §12), padding, short IP retention, no analytics, M6 |

After a failed adoption attempt and a confirmation the user dismisses it (recorded by path and SHA-256); the device then works at its epoch or re-keys again. The same thief can plant account files and markers with fresh salts to make the adoption slow: the adoption groups files by salt, tries eight salts per attempt and lets the user page up to the 64-file scan cap; the marker MAC is checked before that cap (up to 1024 marker files read). A dismissed marker the folder still shows can be listed and restored | accepted (ADR-0063, ADR-0064) |
| R93 | A folder adoption accepts any epoch above the device's own, so an `own + 5` file the typed Secret Key opens is adopted. The typed Secret Key is the authenticator: a file made with keys the user never typed, and any retired or current Secret Key, is refused; a planted header with a high epoch is only a finding and counts for nothing in the target epoch of a re-key. The jump is capped at 16 (R96) | accepted (ADR-0063, ADR-0064) |
| R94 | After an adopted re-key a device holds pushes of its owned vaults the backend has seen until the key of the next generation arrives. A server that withholds that key row keeps the device from publishing those vaults (edits stay local and queued); it cannot make the device seal under the retired key. A vault the backend never saw is not held (nothing of it left the device). Residual: a crash between a backend's create of a vault and the local mark leaves that vault unheld while the backend holds its key under the old AK | accepted (ADR-0063, ADR-0064) |
| R95 | A folder writer can halt or slow an adoption by planting files: more than 1024 marker or account files with low names push the genuine one out of the scan, and a deleted genuine marker or account file stops it as well. It is an availability attack of the same class as deleting files, which any folder writer can do. Recovery: remove the planted files, or set the device up again from the folder's genuine account file | accepted (ADR-0064) |
| R96 | One re-key moves the epoch at most 16 (`MAX_EPOCH_JUMP`). A marker with a larger jump is rejected, and an adoption above `own + 16` is refused. A device that lagged more than 16 epochs behind (many re-keys while it was offline) cannot adopt and must be set up again | accepted (ADR-0064) |
| R97 | Have I Been Pwned and its CDN learn the IP address, the 20-bit prefixes of the checked passwords and their timing; the prefix sets of repeated scans can be linked to one user. The check is opt-in and consented, padded, shuffled, paced and rechecks a row only after 30 days or a password change. HIBP also sees the `User-Agent: Mosaic` marker (a generic one would not hide that the request is a Mosaic scan), the number of requests per scan (about the number of new or changed passwords), and a new prefix right after a rotation, which reveals that a password changed. Users who want to hide the IP use a VPN or an OS proxy (no server proxy, which would tie prefixes to an account) | accepted (ADR-0067) |
| R98 | A wrong HIBP answer (a fault, or a TLS middlebox the OS trust store accepts) hides or invents a breach. A hidden breach is the state without the check; a false report only prompts a password change | accepted (ADR-0067) |
| R99 | A change fill gives the page the current and the new password of one item; same-origin script injection (XSS) on the site gets both, as with any fill, and the site is the recipient by design | accepted (ADR-0068) |
| R100 | A site may apply a change it reports as failed, or the reverse. Every value is kept (the attempt, then the history, and Restore is the rollback); the 32-entry history limit can drop a very old unconfirmed value, and `clear_password_history` keeps unconfirmed values for 30 days only, by the writer's clock. An M7 build on another device has no `reason` and deletes unconfirmed entries, so the invariant needs every device on M7b | accepted (ADR-0066) |
| R101 | The pending value syncs to every device and shared-vault member before the site accepts it, so they can read a password that may never become current | accepted (ADR-0066) |
| R102 | The local store shows a disk reader which item IDs were found in a breach and which are snoozed or dismissed; it holds no password-derived value. The mark is a Lamport stamp (the writer's device ID and edit counter), so a disk reader also sees which device wrote the password; marks of different items can be equal, so rows are only meaningful together with vault, item and field. A random per-item mark was considered and not chosen (ADR-0066) | accepted (ADR-0067, ADR-0069) |
| R103 | Add-origin can extend an item to a hostile subdomain of a registrable domain that hands out subdomains but is not on the public suffix list, after the user's decision in the desktop dialog (https, not loopback, same registrable domain, IDN warning)  The extension no longer offers an address on its own guess: the desktop's public suffix list and the port decide before the offer (two `github.io` tenants are two sites), and the answer checks the role and the attempt again | accepted (ADR-0068, OD-M7b-5) |
| R104 | Attempts started concurrently on two devices: the user may confirm the wrong value; Restore from the history fixes it | accepted (ADR-0066) |
| R105 | CLI session cache: whatever can read both the keystore entry and the session file gets AK without the master password or user verification, **until both parts are deleted, not only for the TTL**. The expiry is checked only when Mosaic opens the file. On Linux the file is in `$XDG_RUNTIME_DIR` (gone at logout; no session without it); on macOS and Windows both parts persist across reboots until swept (every `mosaic` run and the desktop at start, lock and unlock delete expired parts), locked, or deleted by a credential change (password, Secret Key, profile, re-key). A Windows profile backup holds both parts (the keystore blob is DPAPI-protected by the Windows password). A captured pair works with a rewound or faked clock (`libfaketime`, or DYLD injection before hardened runtime, M9) while the parts exist, and AK stays valid until a re-key. Within the TTL any same-user process can also simply run `mosaic get --reveal`; the session adds exposure to copies and clock tricks, not a new class of same-user attack. M9: signed macOS builds run with hardened runtime and an empty entitlements file, which stops DYLD injection into `mosaic`; `libfaketime`-style tricks on Linux, Windows clock changes and unsigned macOS builds remain (R119) | accepted (ADR-0072, ADR-0082) |
| R106 | `mosaic run` puts secrets into the child's environment. Same-user processes can read it on some systems, grandchildren inherit it, and the child may log it. The CLI drops its own session and closes the store before it starts the child (on Unix it `exec`s the child, so no Mosaic process remains). **During the session TTL the child can call `mosaic get --reveal` through the user's session**, so `run` under an open session gives the child every secret, not only the requested ones | accepted (ADR-0075) |
| R107 | Revealed and injected output lands in terminal scrollback, pipes and files the user chose; the clipboard holds the value for its TTL, and clipboard managers or other same-user processes may ignore the history-exclusion hints or read it meanwhile | accepted (ADR-0075) |
| R108 | The exclusive store lock means the CLI and the desktop cannot use one store at the same time (availability). The `own` store is one more device holding AK on the machine (R57a until a re-key) | accepted (ADR-0071) |
| R109 | Terminal input buffers (`rpassword`, the terminal driver) are not wiped; stdin and file-descriptor sources belong to the user's shell; core-dump suppression would need `unsafe` and is not done | accepted (ADR-0074, ADR-0075) |
| R110 | An export file can be guessed offline against its passphrase at the chosen Argon2id cost (standard or stronger) for as long as the file exists; its size and number of chunks are visible. A weak passphrase is only warned about by the client (§5.1). Plaintext export is not offered | accepted (ADR-0073) |
| R111 | Keystore entries the CLI reads (Secret Key, sync tokens, session key) are readable by any same-user process on Windows and Linux; on macOS the keychain asks before another binary reads the desktop's items, but an unhardened binary can be injected into. M9: signed macOS builds are Developer ID signed with hardened runtime and no injection-enabling entitlements, so the keychain's per-binary prompt holds for them; unsigned builds (until OD-M9-3) stay injectable (R119) | accepted (ADR-0072, ADR-0082) |
| R112 | Handoff consent phishing. Someone with the user's password and Secret Key starts a login and sends the user the handoff link. The page asks for the code the user's own desktop shows, and the attacker's link comes with none, so a careful user stops there; the page also shows the requesting device's name and the time. A user who types a code the attacker supplies (read out on the phone, say) and touches the key completes the attacker's login. The second factor never protects vault contents (the password and Secret Key do) | accepted (ADR-0077) |
| R113 | WebAuthn guards access to the server account only, never vault confidentiality. A synced passkey is only as strong as its provider's account (iCloud, Google, a password manager), and Mosaic stores no backup flag to tell synced from device-bound credentials (`passkey-auth` does not expose it). A sign count of 0 on both sides means no clone detection. Authenticators that offer only RS256 cannot register. Attestation is `none`, so any authenticator model is accepted. The relying-party library is young, with one maintainer (ADR-0078) | accepted (ADR-0078) |
| R114 | A malicious browser or browser extension on the user's machine can change the handoff page, read the typed code and use the assertion it obtains, but only for that one handoff, which is bound to the session that created it; it gains no vault data | accepted (ADR-0077) |
| R115 | There is no self-service recovery of a lost second factor: a user who loses every factor asks the operator, who runs `account reset-second-factor`. Whoever convinces the operator gets the reset (it removes the factor, not the password or Secret Key requirement) | accepted (ADR-0077) |
| R116 | Handoffs live in server memory: a restart loses running ceremonies (the user starts again). The per-IP limit of the handoff routes uses the address the proxy reports, with the R62 limits (`trusted_proxies`, IPv6 /64 grouping) | accepted (ADR-0077) |
| R117 | `revoked_sessions` keeps the hashes of revoked tokens with the account, reason and time for 30 days. Whoever holds an old token (a thief included) learns why it stopped working: that the account was re-keyed, the password changed or the device removed | accepted (ADR-0080) |
| R118 | The release and updater keys are CI environment secrets. A takeover of the GitHub account or organisation together with the required reviewer's approval (or a takeover of the reviewer) can sign a release. There is no transparency log; a key rotation is a statement signed with the old key, and a key lost without a signed successor can only be announced | accepted (ADR-0081) |
| R119 | Until the owner has certificates (OD-M9-2, OD-M9-3) the Windows and macOS builds are unsigned: SmartScreen and Gatekeeper warn and users must check `SHA256SUMS` by hand; unsigned macOS builds have no hardened runtime, so R105 and R111 apply in full there, and Touch ID stays hidden | accepted (ADR-0082) |
| R120 | Reproducibility is partial: the Linux CLI, the server binary and image and the extension zips are rebuilt and compared in CI; desktop bundles (WiX, DMG) and every signed binary are not reproducible, and `SHA256SUMS.unsigned` only lets a rebuilder compare the unsigned inputs | accepted (ADR-0086) |
| R121 | Per-user manifests and HKCU keys still override the installer's system manifests in some browsers (Chrome and Edge read HKCU before HKLM on Windows; per-user directories on macOS and Linux), and on macOS the manifests are per-user only. Same-user malware can register its own host; Mosaic detects such overrides and offers a repair, it does not prevent them. Narrows R38 | accepted (ADR-0083) |
| R122 | An oversized vault-metadata merge keeps the longer version and drops the shorter concurrent one; the user is told (`MetaValueDropped`) and can type the dropped value again | accepted (ADR-0085) |
| R123 | The public test server of the security challenge has published credentials, open registration and weekly wipes, and is not production: nothing on it is real data and its operator can read its logs (kept 7 days) | accepted (ADR-0087) |
| R124 | The browser for a handoff opens a URL built from the stored canonical origin. A local writer of the sync configuration (R59) can make it open another site, but that site cannot obtain an assertion for the real server's RP ID (WebAuthn binds the assertion to the RP ID of the page that asks); it can still show a convincing look-alike page, which the writer, already same-user malware (P5, R59), could show anyway | accepted (ADR-0077) |
